      <section id="execution-vs-redress" class="standard-section">
        <h2>Execution vs redress clocks</h2>

        A system executes on its own clock. Redress runs on the institution's,
        which is slower. The gap between them is the window in which a harm
        cannot yet be undone. STD-01 narrows it with hard clocks, reversal, and
        appeal to a human.

        <Std01MicroDiagram />
      </section>

      <section id="preamble" class="standard-section">
        <h2>Preamble: The doctrine of finitude</h2>

        A person's time is finite, and time spent cannot be returned. An
        automated system can issue a decision in milliseconds. The person it
        affects reads it, waits on it, and appeals it at human speed. This
        standard governs the gap between those two speeds and who pays for it.

        When a system wastes a person's time through negligence, obscurity, or
        coercive design, the harm is not a "bad user experience". It is a
        temporal taking: time taken from someone who did not agree to give it.
        It can be measured as a time tax, in hours and in what those hours
        cost the person.

        The taking is hidden by an accounting error, the{" "}
        <a href="/glossary/falsified-denominator">falsified denominator</a>.
        Automation is counted as efficient because throughput and latency are
        measured inside the machine boundary, in milliseconds and server
        cycles. That count leaves out the human work that makes the automation
        usable: the minutes spent on a cryptic error, the hours spent on an
        appeal, the shifts spent repairing model failures by hand. A system
        that counts outside human attention as free and unlimited has
        falsified its denominator. It reports{" "}
        <a href="/glossary/complexity-displacement">complexity displacement</a> as
        operational speed.

        STD-01 sets out seven rights that put that time back in the count. A
        system that violates any article does not comply with STD-01.

      </section>

      <section id="articles" class="standard-section">
        <h2>Article I: The right to stoppability</h2>
        <p class="standard-article-quote">
          A person can stop any process they no longer want to complete.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§1.1</span>
            Immediate cessation: Every active process must have a clearly visible,
            universally accessible control that halts it immediately.
          </li>
          <li>
            <span class="standard-clause-id">§1.2</span>
            Preservation of state: Halting a process must not destroy data as a
            penalty. The system must save the paused state for the maximum
            duration it declares for that state under §3.1, so the user can
            return without penalty.
          </li>
          <li>
            <span class="standard-clause-id">§1.3</span>
            Prohibition of the forced tunnel: An interface must not lock a user
            into a linear sequence, such as a wizard or flow, without a permanent
            exit option on every screen.
          </li>
        </ol>
      </section>

      <section class="standard-section">
        <h2>Article II: The right to exit (resignation)</h2>
        <p class="standard-article-quote">
          A person can always leave, and leaving costs no more than joining did.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§2.1</span>
            Universal exit: A user must be able to end their relationship with a
            system (delete an account, unsubscribe, cancel a contract) with no
            more friction than was required to create it.
          </li>
          <li>
            <span class="standard-clause-id">§2.2</span>
            One-step rule: If entry required one click, exit must require no more
            than one click.
          </li>
          <li>
            <span class="standard-clause-id">§2.3</span>
            Prohibition of retention scripts: A system must not require a user to
            go through a retention flow, exit survey, or confirmation of loss
            before exit. Each is a constructive denial: it blocks exit by adding
            friction.
          </li>
        </ol>
      </section>

      <section class="standard-section">
        <h2>Article III: The right to bounded duration</h2>
        <p class="standard-article-quote">
          Every process has a declared maximum duration, and a stated outcome
          when it runs out.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§3.1</span>
            Hard clock: Every system state must have a defined maximum duration.
            A pending, processing, or reviewing state must not persist
            indefinitely.
          </li>
          <li>
            <span class="standard-clause-id">§3.2</span>
            Timeout guarantee: If a system cannot resolve a request within its
            declared timeframe, it must default to a failure state or to human
            escalation. It must not loop indefinitely.
          </li>
          <li>
            <span class="standard-clause-id">§3.3</span>
            Estimation of burden: Before a user commits to a process, the system
            must declare the estimated time to completion. Concealing how long a
            task takes in order to secure engagement violates consent.
          </li>
        </ol>
      </section>

      <section class="standard-section">
        <h2>Article IV: The right to reversibility</h2>
        <p class="standard-article-quote">
          A person's mistake can be undone without asking anyone's permission.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§4.1</span>
            Undo window: For any action with consequential effects (deletion,
            transfer, publication), the system must provide a grace period in
            which the action can be reversed without administrative intervention.
          </li>
          <li>
            <span class="standard-clause-id">§4.2</span>
            Non-destructive defaults: A system must not permanently destroy user
            data on a single input. Soft delete (archival) must be the default for
            every removal action.
          </li>
        </ol>
      </section>

      <section class="standard-section">
        <h2>Article V: The right to non-coercive waiting</h2>
        <p class="standard-article-quote">
          A person who is kept waiting is told where they stand, is not held on
          the line, and is not left waiting past a stated clock.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§5.1</span>
            Visibility of queue: When a user is placed in a waiting state, the
            system must show their position and expected wait time, accurately
            and in real time.
          </li>
          <li>
            <span class="standard-clause-id">§5.2</span>
            Prohibition of false activity: A system must not use fake progress
            bars, placebo buttons, or looping animations to simulate activity
            while it is idle or stalled.
          </li>
          <li>
            <span class="standard-clause-id">§5.3</span>
            Asynchronous option: A user must not be forced to hold an active
            connection (keep a window open, stay on the phone) to keep their place
            in a queue. For waits exceeding 5 minutes, the system must offer a
            callback or a notification.
          </li>
          <li>
            <span class="standard-clause-id">§5.4</span>
            Expiry default: Where a stated clock for an application, appeal, or
            prior-authorization request expires without a decision, the request
            must resolve in the applicant's favor. Where that default would fall
            harder on the applicant than on the institution, the request must
            instead escalate to a human reviewer. A clock with no stated
            consequence is not a clock.
          </li>
        </ol>
      </section>

      <section class="standard-section">
        <h2>Article VI: The right to reach a human</h2>
        <p class="standard-article-quote">
          An automated denial can be appealed to a person, and the institution
          answers for what its automation does.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§6.1</span>
            Escalation path: Any automated decision that denies a user access,
            service, or property must include a clearly defined path to appeal to
            a human agent.
          </li>
          <li>
            <span class="standard-clause-id">§6.2</span>
            Liability of automata: "Algorithmic error" is not a defense. The
            operating institution must accept full liability for the delays and
            errors of its automated agents.
          </li>
        </ol>
      </section>

      <section class="standard-section">
        <h2>Article VII: The right to transparent burden</h2>
        <p class="standard-article-quote">
          The time a system costs the public is measured and published.
        </p>
        <ol class="standard-clauses">
          <li>
            <span class="standard-clause-id">§7.1</span>
            Cost of compliance: An institution must measure and publish the time
            tax its processes impose on the public.
          </li>
          <li>
            <span class="standard-clause-id">§7.2</span>
            Burden impact statement: Each major system update must be audited to
            confirm it does not increase the cognitive load or the time required
            for existing tasks.
          </li>
        </ol>
      </section>
